# Master Data Services Outline

## Scope

The master-data capability is split into independently deployable bounded contexts. Each service owns its API, persistence, validation rules, and change lifecycle. A service never reads another service's database.

Cross-domain relationships are stored as opaque IDs. They are deliberately not protected by database foreign keys; referential validation happens through APIs or asynchronous events. This keeps each database independently deployable and prevents shared-schema coupling.

The SQL in `database/` targets PostgreSQL. Every subdirectory represents a different logical database and its migration history must be run against that service's own database.

## Bounded contexts

| Service | Owns | External ID references | Does not own |
| --- | --- | --- | --- |
| Vehicle Master | Vehicle identity, specification, lifecycle status, current assignment references | `fleet_id`, `telematics_unit_id` | Fleet profiles, device details, telemetry, maintenance events |
| Telematics Unit Master | Device identity, activation, firmware inventory, capabilities, command eligibility | None initially | Vehicle identity, heartbeats, live connectivity |
| Fleet Master | Customer/fleet identity, tier, SLA classification, operating regions | `preferred_service_provider_id` | Vehicles and provider details |
| Maintenance History | Service and maintenance records | `vehicle_id`, `service_provider_id` | Vehicle and provider profiles |
| Service Provider Master | Provider identity, coverage, capabilities, capacity profile | None initially | Maintenance events and fleet contracts |

Live odometer, health, connectivity, heartbeat, and operational state are not master data. They belong to the Telematics Event or Digital Twin services described in sections 5.3 and 5.4 of `OVERVIEW.md`.

## Vehicle Master Data composition API

The interface described in section 5.1 is an MCP/UCP-facing facade, not a shared database service. It composes results through service APIs:

| Tool | Authoritative call(s) |
| --- | --- |
| `get_vehicle_profile(vehicle_id)` | Vehicle Master |
| `get_vehicle_telematics_unit(vehicle_id)` | Vehicle Master for `telematics_unit_id`, then Telematics Unit Master |
| `get_vehicle_fleet_assignment(vehicle_id)` | Vehicle Master for `fleet_id`, then Fleet Master when details are requested |
| `get_vehicle_service_history(vehicle_id)` | Maintenance History |
| `get_vehicle_current_state(vehicle_id)` | Digital Twin Context, outside master data |

The facade may join responses in memory, but it must not persist copies of another domain's authoritative fields. Partial responses should identify unavailable dependencies rather than silently serving stale joined data.

## Integration outline

- Synchronous reads use versioned HTTP/gRPC service contracts or MCP tool adapters.
- Domain changes publish events such as `vehicle.updated`, `telematics_unit.updated`, and `fleet.updated` through an outbox owned by the publishing service.
- Consumers may build non-authoritative projections in their own databases when needed. Projections record the source ID and version and are never updated by cross-database writes.
- IDs are stable strings generated by the owning service. Examples use prefixes such as `veh_`, `tcu_`, `flt_`, `mtn_`, and `sp_` to make synthetic data easy to inspect.
- Deletes should normally be lifecycle-state changes. Referencing domains tolerate an unknown or retired external ID.
- Each service has independent migrations, credentials, backup/restore, health checks, deployment, and observability.

## Repository outline

```text
services/
  vehicle-master/           # API/application/domain adapters (future implementation)
  telematics-unit-master/   # API/application/domain adapters (future implementation)
  fleet-master/             # API/application/domain adapters (future implementation)
  maintenance-history/      # API/application/domain adapters (future implementation)
  service-provider-master/  # API/application/domain adapters (future implementation)
database/
  <service>/001_create_schema.sql
```

Only service boundary documents and initial database migrations are included at this stage. No runtime, API handler, container, or deployment code is scaffolded yet.

## Suggested delivery sequence

1. Provision one PostgreSQL database and credential per service.
2. Apply each service's `001_create_schema.sql` only to its matching database.
3. Define versioned service contracts and domain events.
4. Implement repositories and application services inside each boundary.
5. Add the MCP/UCP composition facade with timeouts, partial-result handling, and tracing.
6. Add synthetic seed generation through service-owned import commands or APIs.
