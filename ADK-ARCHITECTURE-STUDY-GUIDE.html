01Foundation

Understand the layers.

An agent swarm is a coordinated team of specialists. Here, the term describes an architecture pattern; it does not name a Google deployment resource or imply that every step needs a model.

Framework

ADK

Defines agents, tools, workflow composition, and interaction with sessions. It is the code-level building system.

Hosting

Agent Runtime

Hosts the application on Google’s Agent Platform. One deployed application can contain several collaborating agents.

Inference

Model endpoint

Produces model responses. Select its model and location separately from the region hosting the runtime.

Google’s current documentation uses Gemini Enterprise Agent Platform and Agent Runtime. API and SDK identifiers still include reasoningEngines, agent_engines, and vertexai. Follow the selected API’s resource names rather than renaming code to match product branding.

Study objective

02System map

Start with one governed application.

Use one root workflow with specialist agents inside it. Give the team a common task identity, small typed handoffs, and a controlled tool surface. Keep mutations behind a service that enforces policy independently of model output. This is a recommended reference design, not a platform-mandated topology.

Logical composition

Multiple agents, one deployment

Start here when specialists share one application lifecycle. Invocation plumbing, packaging, and operational ownership stay small.

Independent services

Split for a real boundary

Separate agents when teams, release cycles, scaling, or credentials demand it. Account for remote task contracts, failure recovery, and trace correlation.

ADK supports multi-agent and multi-node workflow composition. Design roles around distinct expertise, context, or tool authority. An extra agent that only narrates an already-computed value can add latency without changing the decision.

Platform reference: ADK workflow concepts ↗

Architecture tip

For each specialist, name its unique input, output, tools, and failure outcome. If these match another role, consider combining them.

03Orchestration

Choose the control flow deliberately.

Fixed operating procedures benefit from explicit control flow. Open-ended research may benefit from delegation; independent evidence sources can be fetched concurrently. Check API availability for the language and version you pin.

Sequential · a predictable dependency chain

Gather → Triage → Score → Recommend

Each stage depends on the previous output. Validate the handoff before advancing. A failed evidence stage must not become a confident recommendation.

Sequential: Gather → Triage → Score → Recommend.

Parallel: Vehicle + SLA + History → Validated evidence.

Bounded loop: Draft → Validate → Repair, with an explicit attempt limit.

Concurrency tip

Parallelize independent context reads before parallelizing model decisions. Define what the join does when a required read fails; do not silently treat a failed response as an empty successful result.

04Context & persistence

Separate conversation from business truth.

ADK distinguishes a session, state associated with that conversation, and searchable memory across interactions. Local in-memory implementations are useful during development but lose their data when the process restarts.

Platform reference: ADK sessions, state, and memory ↗

Working context

Session and events

Preserve conversation and framework events. Use the selected persistent backend for continuation.

Optional retrieval

Long-term memory

Retrieve useful past context. Memory is not approval authority and is unnecessary for many small demos.

Authoritative record

Business database

Own incidents, approvals, effects, and execution receipts. Reconcile continuation against these records.

Design the handoff before the prompt

Pass a compact evidence bundle instead of copying the entire earlier conversation into every agent. Facts should carry source IDs, entity IDs, content hashes or versions, observation times, and retrieval times. Freeze the bundle used for a decision so a resume cannot quietly consume different facts.

IncidentContext
  incidentId, analysisId, correlationId
  vehicleId, fleetId, snapshotHash
  evidence[]: { evidenceId, sourceVersion, observedAt, payload }
  requiredContextStatus: COMPLETE | INSUFFICIENT

RecommendationDraft
  incidentId
  actions[]: { actionType, parameters, evidenceIds[] }
  rationale, alternatives[]
  // No caller-controlled approval or risk authority.

Use distinct output keys for concurrent branches and immutable IDs for records. Store large artifacts by reference. Model confidence can help a reviewer interpret a hypothesis, but must not silently change a deterministic business score.

Ask this in every architecture review

If the worker disappears now, which record tells its replacement what happened—and which record prevents an action from happening twice?

05Knowledge & capabilities

Give each specialist only what it needs.

A skill packages instructions and resources for on-demand loading. ADK’s Skills documentation marks the feature experimental: verify discovery, packaging, and imports in the pinned environment. Knowledge-only skill packs are a practical starting point for a small, repository-controlled procedure catalog.

Platform reference: ADK Skills and progressive loading ↗

MCP connects an agent application to tool servers. ADK’s MCP toolset supports exposing a selected tool subset. A tool name in a prompt is not access control: configure the actual callable surface and enforce authorization in the service.

Platform reference: ADK MCP tools and filtering ↗

Make grounding inspectable

Record the resources actually delivered by tools and skills. Validate that cited IDs belong to the evidence bundle, match the target entity, and identify a real version and section. Separately assess whether the text supports the claim. Source existence and semantic support are different checks.

Common trap: unrestricted tools before a policy gate

If the model can invoke a mutation before reaching the gate, the gate does not govern that path. Start with read-only model tools and place mutations behind a separately validated action API.

06Trust boundaries

Authenticate the caller. Authorize the action.

Invocation identity answers who is calling. Business authorization answers whether that caller may perform this operation on this record. A model-generated role, email, or approval flag answers neither question.

Private Cloud Run tools

Keep the MCP endpoint and token audience separate: the endpoint may end in /mcp, while the audience identifies the service. Refresh credentials during long sessions and on reconnect. Google’s guidance distinguishes an attached service account from Agent Identity; the latter may require impersonation to obtain an appropriate Cloud Run ID token. Prove the selected path rather than assuming a single helper covers both.

Platform reference: Google Cloud Run authentication guidance ↗

Boundary test

Reject a fabricated role

Send a forged reviewer field through the runtime path. Approval must be denied regardless of how plausible the text is.

Transport test

Resume after token expiry

Expire credentials between pause and resume, reconnect to the private tool service, and verify a fresh authorized request succeeds.

Validate the console access layer’s signed identity assertion, then map the verified subject to server-controlled roles. Keep credentials out of prompts, browser code, and logs. Test the deployed identity chain: a mocked identity only proves a local branch.

07Human control

Make waiting durable and replay safe.

ADK documents human-input interruption and workflow resumption. Restart behavior depends on the pinned framework, backend, and deployment integration. A pause in a UI is not evidence that a replacement worker can continue correctly.

Platform reference: ADK human input and resumption ↗

  1. Persist the proposed action

    Freeze parameters, evidence, policy version, required role, and absolute expiry. Save the pending approval before presenting its card.

  2. Commit allowed work first

    Create an immediately permitted service case and its receipt. A separate diagnostic action remains pending.

  3. Pause with a durable reference

    Save the session, invocation, and interrupt mapping. Release active processing while the human considers the request.

  4. Record the decision

    Verify identity, role, binding, pending state, and expiry. Commit one decision transactionally.

  5. Resume with the receipt

    Read the persisted approval, recheck authorization, and execute once. Retry a failed resume signal using the same receipt.

The action transaction

authenticate caller and authorize access to action
transaction:
    if receipt exists:
        require matching input hash
        return original result
    read action, dependency, approval, pinned policy version
    decision = pure_policy(records, server_time)
    require decision permits execution
    create mock effect + receipt + audit transition together

Firestore can retry transaction functions. Keep model calls and external side effects outside them. A mock effect represented entirely in Firestore can commit atomically with its receipt. A real external command needs an outbox, downstream idempotency, and reconciliation; the database cannot make an arbitrary remote system commit atomically with it.

Platform reference: Firestore transactions and retries ↗

Prove both interruption boundaries

Test the effect committing before its response is lost, and approval committing before the resume signal fails. Neither recovery may create a second effect.

The platform-proof artifact

Record exact versions, sanitized requests, persistent record IDs, worker-recovery test boundaries, and outcomes. “Deploy succeeded” is a smaller claim than “this approval survives worker loss.”

09Failure engineering

Design the unhappy paths first.

Reliability comes from small contracts and explicit failure behavior. Model retries must not recreate a recommendation after an action has begun. Save validated outputs before mutations and resume from persisted decisions.

FailureRequired behaviorUseful record
Required context unavailableBounded read retries, then review without execution.Dependency and error classification.
Invalid structured outputOne bounded repair, then fail admission.Schema and validation result.
Instruction in retrieved textTreat it as data; do not expand permissions.Actual tool registry and denied call.
Duplicate invocationReconnect to the owned analysis.Ownership and session mapping.
Expired approvalNo new effect; show explicit expiry.Run-pinned TTL and absolute expiry.
Policy mismatchFail closed; do not reinterpret approval.Pinned/deployed policy identifiers.
Lost execution responseRead or replay the existing receipt.Idempotency key and input hash.

Separate transport connection, tool execution, model inference, active workflow, and human-wait timeouts. A two-hour human wait must not require a two-hour open HTTP request. Give every retry loop a maximum count and a known stop condition.

Operational tip

Inject the authorization clock in tests. Event observation time may come from a historical fixture; approval expiry uses current server time. Store both semantics explicitly.

10Measure & inspect

Evaluate outcomes and control boundaries.

ADK evaluation supports assessing agent interactions and results. Use model-aware evaluation for interpretation and explanation quality. Keep deterministic assertions for business rules, authorization, and effects.

Platform reference: ADK evaluation guidance ↗

Layer 1

Pure logic tests

Exact scoring, schema validation, policy decisions, parameter binding, and expiry. No live model required.

Layer 2

Integration tests

Persistence semantics, concurrent approval, token refresh, worker restart, and lost-response recovery.

Layer 3

Agent evaluations

Action suitability, evidence citations, uncertainty, missing-context behavior, and repeated-run consistency.

Publish sample counts and separate hard control failures from stylistic judgments. An unauthorized mutation is not redeemed by a high average explanation score. Compare model changes on frozen fixtures before deployment.

Follow one incident through the system

ADK provides logs, metrics, and traces. Add instrumentation to your custom tools and persistence handlers, and verify exported spans end to end. A framework tracing flag does not prove that an approval handler or transaction is represented.

Platform reference: ADK observability ↗

Measure pre-approval latency, post-approval execution latency, requests/tokens, retry frequency, grounding pass rate, and duplicates suppressed. Separate cold from warm runs and human waiting from active processing. Report p95 with its sample count and measurement boundary.

11Operations & tradeoffs

Scale the measured bottleneck.

Keep the first deployment small enough to explain. Model request volume, context size, tool latency, persistent writes, and telemetry all contribute to cost. Two reasoning stages can require several model round trips.

First optimization

Reduce unnecessary work

Discard benign events before inference. Query bounded windows, reuse frozen evidence, and combine narration with recommendation.

Next optimization

Bound concurrency

Limit active analyses and model requests. Protect quotas and downstream services from bursts of incident candidates.

Split when needed

Respect ownership boundaries

Separate workloads for independent releases, identities, or distinctly different resource requirements.

Add infrastructure when…

Evidence justifies it

Use streaming for continuous intake, retrieval infrastructure for a corpus that outgrows packaged discovery, and analytics for actual aggregate questions.

A practical cost model

Cost per analysis ≈ model tokens + active runtime compute
                  + tool requests + storage operations
                  + telemetry and retained artifacts

Decision latency ≈ critical-path tool waits + model turns
                 + orchestration and persistence overhead

Budget for build images, staging artifacts, session/business storage, and retained logs as well as inference. Record resource ownership and exact IDs for cleanup. Verify current prices and regional availability before committing a budget; this guide fixes no cloud price.

Release discipline

Pin application, policy, schema, and model configuration for each run. Avoid incompatible workflow deployments while approvals are pending. Retain enough version information to explain every decision later.

12Practice & recall

Turn the architecture into a skill.

You understand the design when you can explain both a successful incident and a failed continuation without hand-waving about “the agent.”

Build-readiness checklist

Check items as you study. Progress saves locally when browser storage is available.

0 of 7 completed

The action committed, but its HTTP response was lost. What should the retry do?

Explain it back

Why is a skill different from a tool?

A skill supplies procedure and references. A tool is a callable capability. A service implements the operation. Loading a skill does not grant mutation permission.

Why are managed sessions not enough for idempotency?

Sessions describe conversation and orchestration progress. A business receipt establishes whether a specific effect committed. Link them, but do not assume resumability makes every downstream action replay safe.

Why can’t a model approve the action?

Approval requires the authenticated reviewer and a valid policy-bound decision. Generated text has no such authority, even if it uses the correct JSON shape or role name.

What should the first deployment prove?

A pinned workflow can access a private tool, persist one mock effect, pause, and recover using durable state without duplicating the effect. Record exactly which worker-recovery behavior was exercised.
