01The scenario

Three signals. One incident.

A NovaFleet van on a strategic fleet develops a power/connectivity pattern. FleetOps gathers context, reasons about the likely cause, and routes a proposed diagnostic through human approval.

18:40 UTC

Low battery voltage

11.4V on veh_10482.

18:45 UTC

Missed heartbeat

The same vehicle stops reporting as expected.

18:47 UTC

Diagnostic failed

A historical, previously authorized attempt failed.

Manual injection places the cluster among roughly 200 ambient events across 100 vehicles. Code validates, deduplicates, sorts by observation time, and finds the three signals within 12 minutes. The console closes ingestion and explicitly starts analysis against a frozen snapshot.

Quiet is a valid outcome

Noise alone yields NO_INCIDENT: no LLM calls, cases, or approvals. Missing required evidence stops execution. Unexpected multiple candidates produce a terminal status; a selection UI is deferred.

02The working team

Two reasoning stages. A governed workflow.

Triage agent

Interpret the evidence

Forms a power/connectivity hypothesis, cites signals and history, and states uncertainty. Receives only read tools and approved skills.

Recommendation agent

Propose the next action

Combines playbook, evidence, and frozen score into a case-plus-diagnostic recommendation. Also explains priority; a separate narration call is unnecessary.

Neither model can create cases, record human decisions, or execute diagnostics directly. Trusted orchestration submits proposals to a private API that validates evidence, policy, parameters, and caller permissions. Customer notifications and firmware actions stay blocked.

04Human control

The case opens. The diagnostic waits.

The case is allowed immediately. The diagnostic requires a verified fleet_ops_manager. Approval binds immutable content, evidence, policy, and expiry. Duration is configured and frozen per run: two hours by default, with a longer option for recordings or restart proofs.

Approval must be recorded before execution.

Approval permits one mock diagnostic; rejection permits none. Repeating a decision returns its stored receipt. The already-created service case remains open.

The planned service commits approval before signaling resume. If signaling fails, retry with the saved receipt. Execution checks for a prior receipt before creating another effect. Rejecting the diagnostic leaves the case open.

Durability is still a proof requirement

A browser refresh is not a worker-restart test. Phase 0 must establish recovery on pinned versions and show that a committed case is never duplicated.

05Four deployables

Where the pieces run.

01 / Cloud Run

Console

Authenticated Streamlit interface: creates runs, starts analysis, shows evidence, and submits verified approve/reject decisions.

02 / Cloud Run

Synthetic data service

FastAPI service writes deterministic batches. The name fleetops-synth-fn is retained, but this is an ordinary service deployment.

03 / Cloud Run

Tools & workflow API

Nine read-only MCP tools and a separate private API for policy, approvals, and mock effects. One container with domain handlers.

04 / Agent Runtime

ADK control agent

One root workflow coordinates two LLM stages and deterministic steps. Session IDs link progress to business records.

Firestore holds events, frozen evidence, one immutable recommendation per incident, approvals, and execution receipts. Rejection reasons stay on inputs or batch receipts. Managed sessions hold continuation state; business records establish whether effects committed.

Master data comes from a finite seeded catalog: 500 vehicles, 20 fleets, 8 regions, and 100 prior incidents. Unknown IDs return errors rather than invented facts.
